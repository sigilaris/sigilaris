# Plan 0033 Phase 4 gate

Phase 4 connects the ordinary HotStuff builder, automatic and explicit durable
voting, actual finalized application and bounded empty progress. Its maintained
contract is described in [ordinary integration](v2-hotstuff-integration.md) and
[finalized application integration](p4-finalized-application.md).

## Implemented boundaries

- The standard proposal-input builder selects an explicit historical profile,
  authenticates the actual parent/QC and retains the full canonical plan before
  emitting its header. Existing body bytes and HotStuff signed layouts remain
  unchanged.
- Activated automatic and explicit voting use actual request authentication,
  certificate import, every selected exact pipeline's readiness, the shared
  durable consensus intent and complete reservations. Header-2 signing without
  an authenticated application/historical profile is refused.
- Actual sink finality invokes authenticated catch-up and ascending application
  publication. Missing material blocks application signing and retries after
  backfill or recovery without undoing accepted consensus facts.
- Empty rounds preserve the actual parent state and reach an explicit finalized
  target after transaction finality. Time and attempt budgets cannot expire
  claims; the maintenance command survives restart.
- The exported four-runtime fixture uses independent identities, stores and
  transport sessions and reconstructs continuous original consensus history on
  file reopen. Its actual V2 votes and application finality are generated by the
  standard runtimes.

shared signing failure fence, complete-context comparison for maintenance targets
and retention of an initially completed command identity. The ordinary signing
review then bound the finalized application runtime to the identical safety store
and kept its gate through actual signing, including a fresh consensus-history
check. An unconfigured legacy signer no longer signs header-2 proposals; explicit
M2 historical authentication remains available because that header predates
application protocol 2.

which cleared existing prepared voting and exact permissions. It retained pending
authenticated finality through delayed observations and reconstructed durable
prepared batches, preserved real conflicting-finality faults through retries,
and compared fresh lower targets with selected canonical history before signing.
The complete pending-target closure is checked before publishing a newly selected
catch-up path, including conflicts between different pending heights.

The actual four-runtime restart exposed fixture evidence being overwritten by
another valid proposal wrapper for the same block. Original proposals are now
retained by proposal identity, and parent/finality lookup follows each actual QC
subject. The fixture also replaced a synthetic historical height gap with the
complete signed old path and authenticated initial-anchor ancestry. Maintenance
commands are forced before requesting progress; same-window conflicts preserve
the valid original intent and store readiness.

Self-review and independent root/core/safety review iterations corrected those
findings. The final shared signing and complete-path-before-commit boundaries
