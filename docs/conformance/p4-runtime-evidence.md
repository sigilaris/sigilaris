# P4 independent runtime evidence

The maintained public fixture is
`release-conformance/shared/v2-jvm/scala/org/sigilaris/conformance/V2RuntimeConformance.scala`,
with its per-node source interpreter in `V2RuntimeMaterial.scala`. The module
wrapper is `V2FourRuntimeConformanceSuite`. Exact final commands are recorded in
the [P4 gate](p4-gate.md).

## Actual runtime and transport

Each cluster creates four ordinary `HotStuffNodeRuntime.create` instances with
automatic consensus, the standard application proposal-input assembly and the
typed durable voting/finalization configuration. Every runtime has one local key,
its own `FileApplicationJournal`, safety state, artifact cache, authenticated
source/recovery verifier and application materializer.

All twelve directed `TxGossipRuntime` sessions perform the actual authenticated
handshake, event polling and reception. Each payload crosses its real encoder and
full-consumption decoder. This is deterministic in-process transport through the
gossip session engine; it does not claim HTTP/TCP socket coverage. Fast lock
contention calls each assembled node's own durable voter and verifies the resulting
independently signed certificate material. Ordinary consensus proposals, votes,
quorums and finality use the gossip sessions.

The inherited fixture trust input is a continuous cryptographically valid legacy
empty history at heights 0–4 and the configured checkpoint/state at height 5. The
height-5 seed is emitted by the ordinary runtime. Every proposal, vote and quorum
from height 6 onward is generated by the four ordinary runtimes. No four-key helper
fabricates future V2 quorums. This checkpoint fixture is distinct from the P5
fresh-bootstrap ceremony and initial-only genesis certificate.

## Seven maintained cases

1. **Execution, empty progress and restart.** The height-6 signed neutral
   application authenticates exact reads, two existing writes and an absent
   creation. Each voter independently verifies the source, plan, inputs, accesses,
   result, owner and actual parent/QC. Actual three-vote quorums finalize it through
   empty children, and all four durable indexes and state roots match. After that
   transaction has finalized, a new maintenance command requests finalized height
   11, beyond its signed deadline 10. The command is forced before notification;
   empty rounds reach the target without new transactions. Reopening each file
   journal and its full proposal/vote archive restores the command, canonical
   application and authentic original history.
2. **Missing preimage.** The leader with a retained local plan can vote; followers
   cannot acquire a consensus intent or emit a vote. Explicit emission through the
   same runtime also fails. No quorum or application forms, and advancing clocks
   beyond the local attempt budget preserves the leader's entire reservation.
3. **Malformed preimage.** Appending a byte to the canonical plan causes the same
   automatic and explicit pre-vote rejection and no-quorum result.
4. **Split honest votes and one Byzantine signer.** Three honest node stores split
   X/Y/X and refuse the other live subject. The fourth votes X durably and is
   deliberately modeled as Byzantine by signing Y outside its honest store. X
   obtains three valid votes; Y has only two and fails certificate verification.
   Reopening all journals preserves the honest refusals and live claims.
5. **Historical anchor ancestry.** A real three-chain and complete signed
   5→4→3→2→1→0 path authenticate the initial-anchor ancestor. A missing block is
   unavailable, and another signed checkpoint fork is rejected.
6. **Conflicting archived finality.** Contradictory but cryptographically valid old
   branches are loaded from actual artifact files and reconstruct the tracker.
   Both latest-finality and vote-publication height fail, even if a higher
   best-finalized candidate is also present. This deliberately models a consensus
   safety fault separately from the honest four-runtime quorum case.
7. **Same-window proposal conflict.** An honest node rejects a valid alternative
   proposal with the same execution/window/root and a changed timestamp. Actual
   request verification precedes `Conflict`; the entire safety snapshot remains
   unchanged and ready. Original-vote retry and file reopen preserve this result.

The distributed reopen is a graceful complete archive/journal reopen. Unknown
writes, cancellation and forced storage boundaries have separate P2/P3 and
[finalized application](p4-finalized-application.md) cases. None of these source
results substitutes for P6's independently resolved staged-artifact consumers.
