# Sigilaris v0.3.0-M3

Status: **prepared locally; not published**. The release tag, remote pushes,
Maven Central upload and public artifact verification remain pending. These
notes describe the frozen M3 candidate, not an available Central release.

M3 adds V2 application execution and durable voting, integrates exact execution
with consensus and finalization, and supplies authenticated new-domain bootstrap
and historical activation. It also updates runtime crypto and TLS dependencies.
This remains a milestone library release; installing it does not automatically
activate V2 or establish a deployment's eligibility to migrate.

## Changes from M2

- Canonical execution plans distinguish complete inputs, lock subsets and
  read/write/creation footprints. Opening validation checks application
  authority, signatures, execution and optional certificates before voting.
- Application votes and complete reservations are journaled before key use.
  Recovery reauthenticates retained original evidence and preserves signing
  fences, exact ownership and historical safety facts.
- Both exact modes feed consensus execution and finalized application state.
  Canonical ancestry is proven from retained proposals and real finality;
  voting and materialization share the signing gate.
- New-domain bootstrap authenticates the signed source bundle, installed
  genesis and initial quorum. Different valid initial quorum vote subsets are
  accepted for the same authenticated subject. Historical handover preserves
  original profiles, the stopped consistency group and key-controller history.
- Never-enabled evidence must cover the full deployment and signer lifetimes.
  Finality observations can be reused only for the same proposal/proof under
  the materializer gate, with failure and cancellation invalidation.
- Runtime dependencies move to BouncyCastle `bcprov-jdk18on 1.86`, elliptic
  `6.6.1`, bn.js `4.12.5`, Armeria `1.41.1`, Netty `4.2.18.Final` and
  netty-tcnative `2.0.84.Final`. Signing requires a 32-byte hash and returns a
  typed failure for invalid input; historical recovery behavior is preserved.
  Source `test`, `testOnly` and `testQuick` verify actual crypto dependencies.

The [V2 evidence map](../conformance/v2-evidence-map.md) links each contract to
its implementation and executable public fixtures.

## Integration and migration

Upgrade all selected Sigilaris modules together. On JVM, replace the old
`bcprov-jdk15on` family and ensure the resolved classpath has exactly one crypto
provider. Scala.js consumers must supply the npm runtime dependencies below;
the library's JAR metadata alone does not install npm packages:

```json
{"dependencies":{"elliptic":"6.6.1","bn.js":"4.12.5","js-sha3":"0.8.0"}}
```

Pass an already computed 32-byte digest to `CryptoOps.sign`. Do not pass raw
messages or truncate arbitrary messages to satisfy the boundary. Valid existing
signatures, Low-S normalization and historical recovery bytes are unchanged.
JVM and JS retain their historical recovery-parameter interpretation; the V2
consumer additionally requires invalid JS parameters to return typed `Left`.

For application integration, start with the [core schema](../conformance/v2-core-schema.md),
[durable integration](../conformance/v2-durable-integration.md),
[exact integration](../conformance/v2-exact-integration.md) and
[HotStuff integration](../conformance/v2-hotstuff-integration.md).
For a new domain, follow [initial bootstrap](../conformance/v2-initial-bootstrap.md)
and install the application's explicit replay policy and authorized opening.
The derived height-0 genesis is an authenticated parent, not a fabricated
proposal or a source-chain finality certificate.

For an existing domain, follow [activation integration](../conformance/v2-activation-integration.md)
and [historical activation](../conformance/v2-historical-activation.md).
Preserve the actual finalized drain checkpoint **F** separately from the
certified continuation parent **P**. Retain and authenticate the original
proposals, QCs, state/results and configuration history from F through P.
Canonical history must reach P under its original profiles before target
application preparation. Conversion runs in the signed compatibility opening;
schema installation must preserve the decoded state.

Back up the complete stopped [consistency group](../conformance/v2-consistency-group.md),
including application/exact/generic pipeline, block, consensus, state,
configuration and controller/evidence namespaces. Keep original signer fences
and the old-context write closure. Do not restore a single namespace in
isolation. Installation and rollback eligibility depend on authenticated
original evidence; changing binaries does not establish that eligibility.

Uninstrumented M1/M2 history cannot acquire missing pre-key promises, original
audit coverage or controller evidence retrospectively. Such deployments cannot
assume an in-place V2 handover is supported. Use the documented source and
issuance contracts to assess the actual retained history. Header version
integers alone do not distinguish the historical release profiles from V2.

## Known limitations and follow-up

The [September 13 crypto audit](../conformance/m3-crypto-security-2026-09-13.md)
records an **unpatched elliptic Low advisory, GHSA-848j-6mx2-7j84**. Its bounded
non-applicability assessment covers the supported secp256k1 `CryptoOps` path
with 32-byte signing hashes; it does not cover arbitrary raw facade use or
other curves. The same dated audit still reports Critical/High findings in
the Scala.js build/development dependency tree, including webpack and
websocket-driver. Runtime remediation does not clear those findings.
[Plan 0035](../plans/0035-scala-js-build-dependency-security-plan.md) owns that
separate work; the release preparation is not a new vulnerability-database audit.

**Immutable M1/M2 JVM artifacts retain `bcprov-jdk15on 1.70`, with five matching
advisories in that dated audit.** M3 does not patch those artifacts. Their
historical conformance profiles intentionally retain that JVM provider; a
compatibility pass is not a security clearance for M1/M2.

[Plan 0034](../plans/0034-v2-recovery-and-lifetime-cost-hardening-plan.md) retains
verified offline corruption repair, checkpointing and journal lifetime costs,
durable leader proposal uniqueness, journal owner binding and callback
reentrancy work. Corrupt tails remain preserved and fail closed; an automated
verified repair procedure is not shipped. Full historical replay can grow
with journal lifetime. The maintenance provider stalls new request identities
after its configured capacity (4096 by default) for that provider instance's
lifetime, and the never-enabled route cannot cover a signer roster
with intervals lacking a key. These are operational constraints, not completed
hardening features.

[Plan 0032](../plans/0032-application-safety-and-exact-pipeline-operational-hardening-plan.md)
also remains open. Static validator sets/topology, operator-managed lifecycle
and fencing, and the absence of a product launcher remain the deployment
baseline. M3 does not introduce automatic failover, arbitrary exact DAGs or
unrestricted cross-pipeline consumption.
