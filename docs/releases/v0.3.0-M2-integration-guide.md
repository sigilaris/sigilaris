# v0.3.0-M2 Application Integration Guide

> **Artifact boundary:** use `0.3.0-M2` for the hardening described here. The
> immutable `0.3.0-M1` artifacts came from tag `v0.3.0-M1` at commit `1c8c2b7`
> and do not contain these source and recovery changes. Upgrade every Sigilaris
> module together and follow the migration below.

This guide is for applications integrating the height-bounded lock and
`exactV2` pipeline contract. The application remains responsible for parsing
its signed plan, transaction families, dependency reference, and business
result. Sigilaris treats those values as opaque verifier output.

## Dependencies

Use one version for every Sigilaris module. Shared contracts are published for
both JVM and Scala.js; the runtime is JVM-only.

Scala.js applications must also install the JavaScript runtime dependencies
`elliptic@6.5.4` and `js-sha3@0.8.0` through their npm/bundler setup.
Maven resolution alone does not install them. The standalone `release-smoke`
build demonstrates a locked npm setup.

```scala
val sigilarisVersion = "0.3.0-M2"

libraryDependencies ++= Seq(
  "org.sigilaris" %%% "sigilaris-core"        % sigilarisVersion,
  "org.sigilaris" %%% "sigilaris-node-common" % sigilarisVersion,
  "org.sigilaris" %%  "sigilaris-node-jvm"    % sigilarisVersion, // JVM only
)
```

The protocol types are under `org.sigilaris.core.application.protocol`, exact
pipeline request and manifest types are under
`org.sigilaris.node.txpipeline`, and JVM coordination is under
`org.sigilaris.node.jvm.runtime.application` and
`org.sigilaris.node.jvm.runtime.txpipeline`.

## Register And Activate A Profile

1. Implement `ApplicationExactPipelineVerifier[F]`. It must authenticate and
   decode the signed application plan and both transaction payloads, then
   return one `VerifiedExactDependencyPlan` with exactly two ordered execution
   ids, producer position `0`, consumer position `1`, one opaque dependency
   reference, one execution mode, and one common inclusion deadline.
2. Register the implementation by the exact `(verifierSlot,
   verifierManifestDigest)` pair committed in the deployment manifest.
3. Put the matching profile id and version in
   `ApplicationProtocolManifestV1`. Profile ids and slot/digest pairs
   must be unique.
4. Open the application safety and exact admission stores and call
   `ExactPipelineStartupGate.reconcile` before binding public listeners or
   producing proposals.

The startup gate compares the configured manifest, registry, journal replay,
exact admission projection, and physical store schema. A disagreement is a
hard startup failure; do not repair one namespace independently.

The manifest must set block header `2`, execution plan `1`, lock `1`, effect
`1`, exact pipeline `2`, and application journal `1`. The configured maximum
lock lifetime is consensus-visible, and every accepted deadline must be after
the admission base height and within that bound.

## Submit And Query Exact Work

Exact requests use the existing pipeline route with a required discriminator:

```http
POST /tx-pipeline
Idempotency-Key: application-operation-123
Content-Type: application/json

{
  "kind": "exactV2",
  "request": {
    "transactions": ["signed-producer", "signed-consumer"],
    "signedApplicationPlan": "signed-plan",
    "profileId": "neutral.bytes32",
    "profileVersion": 1,
    "waitFor": "finalized"
  }
}
```

The application verifier, not Sigilaris, interprets the signed strings. A
byte-equivalent replay with the same key may change only `waitFor`; it returns
the original identity. Reusing a key for different work returns
`idempotencyConflict`.

Multiple idempotency keys may intentionally alias the same immutable exact
submission. Alias repair never changes the canonical record or permits one key
to identify different content; it only restores a missing secondary binding
after the primary submission has been matched.

## Migration From M1 To M2

M2 contains source-incompatible hardening relative to the published M1
artifacts. Update integrations as follows:

- construct `ExactPipelineAdmissionService` with its effectful `create`
  factory and provide `ApplicationSafetyRuntime`;
- handle `ApplicationProtocolManifestV1.withComputedDigest` and
  `computeConfigurationDigest` as `Either` results, or use the explicitly
  named unsafe fixture helper only in trusted setup code;
- handle `BlockStore.putHeader` as an `EitherT` because invalid versioned
  commitments are rejected before persistence;
- preserve `ApplicationSafetyState.terminalExecutions` and use
  `expireExecution` so an expired identity cannot be forgotten when its input
  rows are reassigned;
- update exhaustive matches for new application-safety, input-validation, and
  manifest-validation failure cases, including terminal-execution rejection;
- mount `applicationStatusEndpoint` explicitly on an authenticated operator
  plane because default exact endpoint bundles no longer include it;
- treat certified/finalized waits as exponentially backed off and capped at
  five minutes, including an absent configured timeout;
- allow startup to commit the one-time `repairLegacyDrainState` migration when
  an older coherent journal contains live exact work without a covering drain
  watermark; back up the complete consistency group before the first upgraded
  start;
- preserve journaled terminal exact rows across profile retirement. Current
  policy is enforced for new and nonterminal work, while terminal historical
  replay remains available after rotation;
- implement `ExactTxPipelineStore.getByRequestIdentity` in custom stores and
  maintain request, application-pipeline, execution, and reference ownership
  indexes atomically with primary exact rows; admission no longer falls back to
  full record listing for replay or uniqueness checks;
- implement `ExactTxPipelineStore.countUnjournaled(journaledPipelineIds, stopAt)`
  with one bounded primary-key scan, counting rows absent from the application
  journal up to `stopAt` (zero for nonpositive limits). Do not repeatedly decode
  or sort complete record pages for the admission-capacity check;
- require every configured and persisted verifier manifest digest to be
  canonical 32-byte lowercase hex. An older programmatic manifest that bypassed
  decoder validation has no automatic rewrite because the digest participates
  in configuration identity; drain and rotate it with the previous binary
  before upgrading to M2.

The [M2 release notes](v0.3.0-M2-release-notes.md) record the release source
and artifact verification.

Query the returned node pipeline id with `GET /tx-pipeline/{pipelineId}`. The
combined query refuses an id that appears in both generic and exact physical
namespaces. The optional operator-only
`GET /tx-pipeline/application-status` endpoint exposes schema-v1 aggregate
lock, reservation, deadline, drain, profile, mode, lifecycle, and durable
failure diagnostics without exposing opaque application payloads. It has no
built-in authentication and is not mounted by the default exact endpoint list;
mount `applicationStatusEndpoint` only behind the embedder's authenticated
operator plane.

## Choose The Execution Mode

- `orderedAtomic` places producer and consumer in one ordered execution wave.
  The working state is committed only when both application reductions and
  their declared result/state commitments validate; otherwise no partial
  canonical state is visible.
- `certifiedAncestor` records the producer first and admits a consumer only
  when the named producer is a certified ancestor and its exact result is
  available. Adjacency is an optimization, not a validity rule.

Both modes use the same inclusive `lastInclusionHeight`. A live entry expires
as `expiredUnapplied` only after finalized canonical height becomes strictly
greater than that deadline. Wall-clock time, best height, and certified height
cannot release a lock.

## Rotation And Recovery

Configuration rotation is drain-to-empty: close admission, continue canonical
application and finalized-height expiry, wait until finalized height is past
the greatest admitted deadline and live locks, reservations, and nonterminal
exact pipelines are zero, activate the new manifest atomically, then rerun
startup reconciliation. Accepted exact work raises the watermark at journal
registration even before a lock certificate exists. A non-empty domain cannot
be overridden.

The exact admission store rebuilds request and ownership indexes from its
immutable primary rows when it opens. This startup scan replaces per-submission
full-record scans. The resident indexes contain only pipeline identifiers,
request identities, ownership commitments, and idempotency bindings; complete
transaction payloads remain in the primary store and are read under the store
gate for immutable replay comparison. Malformed or conflicting rows are a
startup error whose diagnostic names the offending durable key. Explicit
listing applies the requested primary-store page before decoding rather than
decoding the whole namespace. The indexes are derived state and do not
introduce a new persistent format. Listing order is implementation-specific:
SwayDB uses serialized-key order, while the in-memory store uses pipeline-id
string order. Consumers must not rely on identical ordering across backends;
startup reconciliation is order-independent and runs before admission starts.

If an exact-primary write fails after its durable outcome becomes ambiguous,
the current process invalidates its derived indexes and fails indexed work
closed. Restart the store session to rebuild from primary rows after resolving
the storage failure; do not attempt to reconstruct an index manually.

Never rotate a store set that has not passed reconciliation under its current
manifest. If recovery finds an admission row for a profile that the target
manifest removes, restart with the current manifest, reconcile that row into
the journal, and drain it to a terminal lifecycle before activation. Do not
delete the row or bypass profile validation. After activation, an
already-journaled terminal row is retained and may be replayed without the
retired profile; new or nonterminal rows still require the active profile.

On the first upgraded start, a coherent older journal may contain live exact
work without a drain watermark that covers its deadline. The application store
derives the greatest live deadline, demotes an unsafe `ready` or `activating`
phase to `waitingFinality`, and commits one `repairLegacyDrainState` entry. A
second restart is a no-op. Physical state that does not exactly reproduce the
pre-repair journal remains a hard startup failure. The default SwayDB recovery
observer emits one warning with the repair sequence and before/after phase and
watermark, so operators can distinguish an expected legacy migration from a
new producer of under-recorded state. This warning is best-effort: a crash
after the repair is prepared or committed but before notification can leave no
warning, including after restart. The `repairLegacyDrainState` journal entry
is the authoritative recovery record; absence of a warning does not prove that
no repair occurred.

Back up the application safety, journal, exact admission/idempotency, generic
pipeline, block, consensus, and state namespaces as one stopped-node
consistency group. On restore, replay the journal and pass the complete startup
gate before reopening admission.
